# Nathenael Tamirat — Portfolio

A production-ready personal portfolio built with Next.js, React, TypeScript, and
the App Router. The application is statically generated by default and uses a
small client boundary only for navigation and the certificate carousel.

## Architecture

- `app/` — routes, layouts, metadata, error states, sitemap, robots, and manifest
- `components/` — reusable navigation, content sections, cards, carousel, and JSON-LD
- `lib/` — typed portfolio content and site configuration
- `hooks/` — isolated client interaction state
- `public/` — optimized-at-request-time source media
- `styles/` — shared design tokens
- `types/` — domain models
- `utils/` — framework-independent helpers

All portfolio content is centralized in `lib/content.ts`. Routes render on the
server and are prerendered as static HTML. `next/image` reserves image dimensions
and negotiates AVIF/WebP where the deployment platform supports image optimization.

## Local development

Requirements: Node.js 22+ and npm.

```bash
cp .env.example .env.local
npm ci
npm run dev
```

Set `NEXT_PUBLIC_SITE_URL` to the deployed HTTPS origin so canonical URLs,
Open Graph URLs, the sitemap, robots directives, and structured data use the
correct production domain.

## Migration summary

Before:

- one large HTML document plus eight placeholder pages
- global CSS organized around element IDs
- global inline carousel handlers
- duplicated page metadata and stylesheet references
- no real build, dependency, lint, type, CI, sitemap, robots, or deployment setup
- broken fragment/case-sensitive asset references and unoptimized media delivery

After:

- nine App Router routes with reusable, strongly typed components
- server-first static generation with minimal client JavaScript
- shared content, metadata, navigation, layouts, and design tokens
- responsive images with reserved dimensions and AVIF/WebP negotiation
- accessible landmarks, headings, focus states, skip link, mobile navigation,
  reduced-motion support, and keyboard-operable carousel
- per-page canonicals, descriptions, Open Graph/Twitter metadata, sitemap,
  robots, manifest, Person/WebSite/Breadcrumb structured data
- custom loading, error, and not-found experiences
- CSP and defensive response headers, long-lived asset caching, compression,
  CI, ESLint, Prettier, and strict TypeScript

`Organization`, `Article`, and `FAQPage` schemas are intentionally absent:
the source content does not establish an organization, articles, or FAQs.
Publishing unsupported schema would reduce data quality rather than improve SEO.

## Deployment

Vercel is the recommended target because it supports the Next.js image optimizer,
immutable framework assets, compression, preview deployments, and response headers
without additional infrastructure. Connect the repository, set
`NEXT_PUBLIC_SITE_URL`, and use the standard `next build` command.

For another Node host, run `npm ci`, `npm run build`, and `npm start` behind an
HTTPS reverse proxy/CDN. Preserve the headers from `next.config.ts` and cache
`/_next/static/*` immutably. A purely static export requires additional image
configuration and is not the default production target.

The CSP permits inline scripts/styles required by the current Next.js rendering
and trusted JSON-LD. A nonce-based CSP can be stricter, but requires dynamic
request rendering and should be adopted only if that performance trade-off is
acceptable.

## Production checklist

- [x] Static generation for all public routes
- [x] Unique titles, descriptions, canonical URLs, Open Graph, and Twitter cards
- [x] XML sitemap, robots.txt, web manifest, and valid applicable JSON-LD
- [x] Semantic heading hierarchy, landmarks, breadcrumbs, and internal links
- [x] Responsive/lazy images, explicit dimensions, LCP preload, AVIF/WebP support
- [x] Keyboard navigation, visible focus, reduced motion, and labelled controls
- [x] Mobile-first layouts across phone, tablet, laptop, and wide screens
- [x] Strict TypeScript, ESLint, Prettier, CI, 404, loading, and error boundaries
- [x] CSP, clickjacking/MIME/referrer/permissions headers, caching, and compression
- [x] Zero known npm audit vulnerabilities at migration time
- [ ] Set the real `NEXT_PUBLIC_SITE_URL` in production
- [ ] Run Lighthouse against the deployed URL; scores depend on hosting, network,
      browser, and the configured production domain and cannot be guaranteed by source alone
